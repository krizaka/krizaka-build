---
title: Clés d'idempotence
description: krizaka-idempotency — une action HTTP s'exécute au plus une fois par Idempotency-Key ; une reprise rejoue sa réponse.
---

```xml
<dependency>
  <groupId>com.krizaka</groupId>
  <artifactId>krizaka-spring-boot-starter-idempotency</artifactId>
</dependency>
```

Un client dont la connexion a coupé après que ton service a accepté une requête ne peut pas savoir si elle a abouti.
Réessayer à l'aveugle fait payer deux fois, ne pas réessayer perd la commande. Avec un en-tête `Idempotency-Key`, la
reprise est sûre — promu depuis Orazaka, où chaque lancement payant fonctionne ainsi.

```yaml
krizaka:
  idempotency.store: jdbc
spring.sql.init.schema-locations: classpath:com/krizaka/idempotency/schema-postgresql.sql
```

```java
@PostMapping("/api/v1/orders")
ResponseEntity<Order> create(@RequestBody NewOrder order, @AuthenticationPrincipal Jwt caller,
    @RequestHeader(value = IdempotencyKeys.KEY_HEADER, required = false) String key) {
  return idempotency
      .execute(new IdempotentRequest("orders.create", caller.getSubject(), key, order),
          Order.class, () -> orders.create(order))
      .toResponse(HttpStatus.CREATED);
}
```

## Le contrat

| Requête | Réponse |
| :-- | :-- |
| première, avec une clé | l'action s'exécute ; sa réponse est stockée dans la transaction de l'action |
| reprise, même clé, même requête | la réponse stockée, avec `Idempotent-Replayed: true` — l'action ne s'exécute pas |
| même clé, autre requête | `422` Problem Details, code `idempotency-key-reused` |
| deux à la fois, même clé | la seconde attend la clé, puis rejoue la première |
| l'action échoue | rien n'est enregistré : la reprise s'exécute pour de vrai |
| sans clé | l'action s'exécute, à chaque fois |
| une clé malformée | `400` Problem Details, code `invalid-idempotency-key` (1 à 255 caractères ASCII visibles) |

Une clé appartient à un scope et à un sujet : la clé d'un client ne rejoue jamais celle d'un autre. La requête est
empreinte par le SHA-256 de son JSON canonique : l'ordre de ses champs n'est pas une différence. Les clés sont gardées
`krizaka.idempotency.ttl` (24 heures) et purgées à intervalle.

## Prouvé

`JdbcIdempotencyIT` l'exécute sur PostgreSQL — rejeu, réutilisation, annulation, deux requêtes simultanées sur une clé,
purge — et [l'application d'exemple](https://github.com/krizaka/krizaka-platform-kit/tree/main/examples/krizaka-idempotency-example)
le prouve en HTTP. Chaque exécution est observée en `krizaka.idempotency` (voir [Observabilité](/observability)).
